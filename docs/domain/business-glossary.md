# 비즈니스 용어 사전

> 코드에 직접 나오지 않지만, PR 리뷰 시 알아야 하는 비즈니스 맥락입니다.

## 핵심 도메인 용어

| 용어 | 의미 | 코드에서 왜 중요한가 |
|------|------|---------------------|
| PR 리뷰 병목 | 시니어 1~2명에게 리뷰가 몰리는 현상. 평균 리뷰 대기 45분 | 이 프로젝트가 존재하는 이유. 자동화로 45분 → 10분 목표 |
| 컨벤션 위반 재발 | 같은 개발자가 같은 규칙을 반복 위반. PR당 평균 2.3회 | convention 노드 + author_history 메모리의 존재 이유 |
| 사이드 이펙트 | 코드 변경이 의도치 않게 다른 모듈에 영향을 주는 것 | impact 노드의 BFS 호출 그래프 탐색이 이걸 잡아냄 |
| AI 시나리오 검증 | pytest 실행 대신 Claude가 "이 코드가 시나리오를 충족하는가" 판단 | Docker 의존성 문제로 코드 실행 방식에서 전환한 핵심 결정 (ADR-003) |
| graceful degradation | 일부 기능 실패해도 전체 서비스가 중단되지 않는 설계 | ChromaDB 꺼져도 분석 진행, LLM 실패해도 노드 SKIPPED 처리 |

## 사용자가 자주 묻는 질문 (FAQ)

**Q: 왜 테스트를 직접 실행하지 않고 AI가 판단하나요?**
A: 초기에는 Docker에서 pytest를 실행했으나, 외부 라이브러리 의존성, mock 불일치, 실행 환경 차이로 생성된 테스트의 80%가 환경 문제로 실패했습니다. AI 시나리오 방식은 비즈니스 로직 검증에 집중할 수 있어 전환했습니다.

**Q: 컨벤션 검사에서 AST와 LLM을 왜 둘 다 쓰나요?**
A: AST는 빠르고 정확하지만 "가독성", "로직 중복" 같은 주관적 판단이 불가합니다. LLM은 이런 복잡한 패턴을 잡아주지만 느리고 비쌉니다. diff 8KB 이하일 때만 LLM을 추가 호출하는 하이브리드 전략으로 비용과 품질을 균형잡았습니다.

**Q: 리스크 레벨은 어떻게 결정되나요?**
A: 점수 기반입니다. 영향 모듈 수 × 2 (최대 10점) + API 변경 시 +5점 + 핵심 파일(auth, payment, security, database, migration) 변경 시 +3점. 합산 15점 이상이면 Critical입니다.

**Q: RAG 도메인 문서를 바꾸면 어떻게 되나요?**
A: docs/domain/ 디렉토리의 마크다운을 수정한 후 ChromaDB에 재인덱싱하면 됩니다. 다른 프로젝트에 이 Agent를 붙일 때 해당 프로젝트의 비즈니스 문서로 교체하면 도메인에 맞는 리뷰가 생성됩니다.
